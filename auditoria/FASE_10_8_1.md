# Fase 10.8.1 — Correção e validação do TLS MySQL

## Status

Foi corrigida e testada, com certificados e servidor de protocolo fictícios, a
verificação da identidade IP TLS usada pelo perfil Feira. **Nenhum MySQL real
foi acessado**, nenhuma configuração do Windows ou serviço foi alterada e
nenhuma instância foi provisionada ou iniciada.

Esta validação não autoriza o provisionamento da instância nem a primeira
execução do Node.js.

## Causa confirmada

O projeto utiliza `mysql2` 3.24.6. Na implementação instalada,
`lib/base/connection.js` deixa `servername` indefinido quando o host é um IP
literal. A validação posterior de identidade do driver só compara o
certificado quando `servername` é uma string. Assim, `verifyIdentity: true` e
`rejectUnauthorized: true` validam a cadeia confiável, mas não garantem que o
certificado corresponda ao SAN IP `127.0.0.1`.

Os testes também reproduziram a interação com o TLS do Node.js: para o IP
literal, a identidade precisa ser verificada explicitamente contra o host
configurado. Não basta confiar na CA ou apenas inspecionar as opções do pool.

## Correção implementada

- [`lib/mysql-tls-identity.js`](../renolink_funcional/lib/mysql-tls-identity.js)
  exige certificado, exige SAN do tipo IP correspondente ao host e chama
  `tls.checkServerIdentity`. Ausência do certificado, SAN incorreto ou
  indisponibilidade/falha do verificador resulta em erro.
- [`lib/mysql.js`](../renolink_funcional/lib/mysql.js) instala o verificador
  somente quando `APP_ENV=fair` e TLS está ativo. A validação do destino Feira
  exige CA, validação da cadeia e o verificador previsto. Outros perfis não
  recebem a opção adicional.
- [`scripts/patch-mysql2-ip-identity.js`](../renolink_funcional/scripts/patch-mysql2-ip-identity.js)
  aplica um patch localizado e idempotente ao `mysql2` 3.24.6. Para IP literal,
  mantém `rejectUnauthorized` para validar a cadeia, evita que o callback
  automático compare o IP com um nome alternativo e executa a verificação
  explícita contra o host configurado antes do pacote de autenticação MySQL.
  Rejeita versões e trechos de código inesperados.
- [`package.json`](../renolink_funcional/package.json) aplica o patch no
  `postinstall` e inclui os novos testes no comando `npm test`.
- [`test/mysql.tls.identity.test.js`](../renolink_funcional/test/mysql.tls.identity.test.js)
  negocia TLS real com um servidor local fictício que implementa o início do
  protocolo MySQL e verifica se o pacote de autenticação foi enviado.
- [`test/fixtures/generate-mysql-tls-fixtures.ps1`](../renolink_funcional/test/fixtures/generate-mysql-tls-fixtures.ps1)
  gera somente certificados fictícios. As fixtures e sua descrição estão em
  [`test/fixtures/mysql-tls/`](../renolink_funcional/test/fixtures/mysql-tls/).
  A chave privada da CA sintética não é mantida.

O patch não desativa a verificação da CA, não usa
`rejectUnauthorized: false` e não aceita certificados apenas por serem
assinados por uma CA privada. Certificados com CN coincidente, mas sem SAN IP,
também são rejeitados.

## Testes e resultados

Executado `npm run postinstall`: o patch instalado foi reconhecido como
aplicado e idempotente.

Executado `npm test`: **84 testes passaram; 0 falharam**. A suíte incluiu:

| Cenário | Resultado |
|---|---|
| Cadeia confiável e SAN IP `127.0.0.1` | Aceito |
| SAN IP diferente | Rejeitado antes da autenticação |
| Sem SAN IP, mesmo com CN correspondente | Rejeitado antes da autenticação |
| CA não confiável | Rejeitado antes da autenticação |
| Certificado expirado | Rejeitado antes da autenticação |
| Verificador de identidade que retorna erro | Rejeitado antes da autenticação |
| Verificador TLS indisponível | Helper falha de forma fechada |
| Perfil Feira | Verificador estrito configurado |
| Perfil existente sem configuração Feira | Sem callback Feira adicional |

O servidor do teste escutou apenas em `127.0.0.1` numa porta efêmera. As
credenciais, certificados e chaves usadas são exclusivamente fictícios. A
suíte não conectou a MySQL, não iniciou o servidor RenoLink e não acessou
recursos externos.

## Revisão estática do bootstrap MySQL

Foi consultada, sem iniciar o servidor, a ajuda do executável local
`D:\MySQL\bin\mysqld.exe` com `--no-defaults --verbose --help`. Ela indica:

- `--enable-named-pipe`: “Only to be used for the default server (NT)”;
- a opção `named-pipe-full-access-group` existe, mas a ACL efetiva do pipe não
  foi comprovada;
- shared memory está desativada por padrão; sua ACL e sua adequação ao bootstrap
  de uma segunda instância também não foram comprovadas.

Portanto, o bootstrap proposto na Fase 10.8 com `skip-networking=ON` e named
pipe **não está aprovado para a instância não padrão
`MYSQL_RENLINK_FEIRA`**. Não se deve executar seus comandos como estão. Isso é
especialmente importante porque `--initialize-insecure` deixa a conta root sem
senha; sem transporte local e ACL comprovadamente restritos, iniciar o serviço
criaria risco de acesso local não autorizado.

Nenhum bootstrap foi executado. Antes de autorizá-lo, é necessário escolher e
validar um método de acesso local compatível com uma segunda instância e
demonstrar suas ACLs efetivas sem expor root sem senha. O método para definir e
armazenar a senha inicial também continua pendente; nenhum cofre foi acessado.

## Limitações e riscos restantes

- O handshake testado usou um servidor MySQL simulado, não MySQL 8.0.46. A
  validação não comprova a configuração TLS, certificado ou listener de uma
  instância real.
- O patch é específico para `mysql2` 3.24.6 e altera `node_modules` no
  `postinstall`. A dependência declarada permite versões posteriores; se a
  versão ou trechos esperados mudarem, o script falha deliberadamente e exige
  revisão. O patch também precisará ser reavaliado em futuras atualizações do
  driver.
- Os testes não validam a instalação/ACL da CA e da chave do servidor, a
  identidade `server_uuid`, a conexão autenticada ao banco nem os privilégios
  MySQL.
- As fixtures são para teste e não devem ser reutilizadas como certificados ou
  chaves operacionais.
- O procedimento de bootstrap da Fase 10.8 permanece bloqueado até a solução
  de transporte local e armazenamento seguro da credencial inicial.

## Impactos em outros ambientes

O código do verificador adicional é selecionado somente por `APP_ENV=fair`.
Para configurações existentes sem esse perfil, o callback não é adicionado; a
suíte confirmou essa diferença. O patch instalado no `mysql2` preserva o
caminho original quando a opção customizada não foi configurada.

O `postinstall` e a alteração em `node_modules` ficam restritos a esta cópia do
projeto, mas uma instalação que resolva versão incompatível do `mysql2` será
interrompida pelo script até revisão. Não houve alteração de outro projeto,
MySQL, Firewall, SSH, serviço ou configuração global.

## Condições para autorizar o provisionamento

Antes de qualquer criação ou inicialização:

1. Revisar/aprovar a estratégia de patch do `mysql2` 3.24.6 ou substituí-la por
   versão cuja identidade IP esteja comprovada por teste equivalente.
2. Confirmar o certificado operacional com SAN IP `127.0.0.1`, período válido,
   CA aprovada e arquivos/ACLs corretos; não usar as fixtures.
3. Definir, com autorização própria, um método de bootstrap compatível com uma
   segunda instância e provar o isolamento/ACL antes de iniciar com root sem
   senha. O procedimento de named pipe da Fase 10.8 não deve ser usado sem essa
   revalidação.
4. Definir o armazenamento seguro da senha inicial sem expô-la em argumentos,
   histórico, logs, transcrição ou arquivos acessíveis indevidamente.
5. Manter a confirmação explícita exigida para qualquer operação administrativa,
   criação de serviço, início de serviço, conexão ao banco ou criação de schema
   e usuário.

## Plano de reversão

Se a correção for rejeitada antes do provisionamento, reverter os arquivos
listados na seção “Correção implementada”, remover a entrada `postinstall` e
restaurar a dependência conforme o lockfile, sempre preservando quaisquer
alterações independentes existentes. Nenhuma reversão foi executada. Não há
serviço, banco ou recurso externo desta fase para remover.
